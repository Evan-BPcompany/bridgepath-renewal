# PRD: Bridge Path OEM/ODM 제조·무역 의뢰 웹서비스

## 진행 상태 (다음 세션 시작점)

**현재 위치**: MVP Scope의 "1순위 열린 질문(개발 착수 전 필요)" 7개 중 6개 반영 완료, **항목 7/7 "예상 제작기간을 계산하거나 안내하는 기준"**이 아직 미확정 — 다음 세션은 여기서 시작한다.

- 항목 7의 A/B/C안(가격과 동일한 수량구간 구조 / 품목별 대략 범위만 / MVP에서 표시 안 함)을 다시 보여주고 결정하는 데서 이어간다.

**다음 세션 진행 순서**:
1. 예상 제작기간 기준 A/B/C안 재검토 및 결정
2. 1순위 열린 질문 7개 반영 결과 전체 점검
3. 남은 2순위 열린 질문 검토
4. PRD 전체 일관성 및 누락 검토
5. PRD 확정 여부 결정

**이번 세션에서 새로 확정된 것**: FR-9(제품 카테고리 구조), FR-10(견적 요청 진입 흐름), FR-1.6(카테고리 4 지원 유형별 입력), FR-4.2(고객 유형: 개인·창업 준비 중 / 사업자·브랜드 운영 중), FR-5.5(관리자 처리상태 10개), FR-2.6~2.11(첨부파일 형식·개수·용량 제한), FR-3 전면 재정의(AI 사전 가격안내 — 수정된 D안), FR-3.13(가격 근거 3종 분리 + 1688/Alibaba API 기술검증 과제), FR-3.14/3.15(정식 견적 요청 vs AI 예상가격의 최소정보 분리, 표준 사양 확인 흐름).

## User Journeys

### UJ-1: 선글라스 신규 브랜드 제작 의뢰 (전체 목표 시나리오)

> 아래 여정은 사용자가 그린 **이상적인 전체 사용자 여정**이며, 여기 나온 모든 기능을 MVP에 포함한다는 뜻이 아니다. 로그인·마이페이지·알림·AI 예상견적·제작현황이 전부 MVP에 포함된다는 뜻이 아니며, MVP 범위는 이 여정을 기준으로 별도로(아래 MVP Scoping 참고) 정한다.
>
> - 8번의 "Bridge Path 담당자" 검토·정식 견적 작성은 실제로 필요한 관리자 기능이며, 별도의 관리자 관점 사용자 여정(UJ-2, 추후 작성)에서 구체화한다.
> - 5번의 AI 예상견적은 중요한 목표 기능이지만, 공장 가격 데이터와 계산 기준이 충분하지 않으면 정확히 구현하기 어려울 수 있다. MVP 포함 여부와 구현 가능성은 아래 MVP Scoping에서 별도로 검토한다.
> - 고객에게 보이는 **AI 예상견적(참고용 범위)**과 담당자가 공장 확인 후 발행하는 **정식 견적**은 항상 명확히 구분되어야 한다.
> - 운송·통관 등 실비 항목은 실제 조건에 따라 달라질 수 있다 — 이 여정에 나온 금액·항목은 예시이지 확정값이 아니다.

**주인공**: 민수 — 온라인 쇼핑몰과 SNS에서 자체 패션 브랜드를 운영하는 국내 소규모 사업자. 기존에는 완제품을 사입해서 판매했지만, 이번에는 브랜드 로고와 원하는 디자인을 적용한 선글라스를 자체 제작하고 싶다. 중국 공장을 직접 찾거나 알리바바 업체와 중국어로 소통하고, 품질·운송·통관까지 처리하는 것이 어렵고 불안하다.

1. 검색이나 지인 소개로 Bridge Path 홈페이지에 들어와서, 공장을 직접 운영하는 회사가 아니라 실거래 경험이 있는 중국 제조업체·포워딩 파트너와 함께 OEM/ODM 제작과 무역을 관리하는 회사라는 설명을 본다.
2. 선글라스 제작 경험, 가능한 제품 종류, 소재, 제작 절차, 실제 사례를 확인하며 "이 회사는 단순 중개가 아니라 제작 과정을 이해하고 있다"는 신뢰를 얻는다.
3. '선글라스 예상견적 받기'를 선택해 원하는 종류, 프레임 소재/색상, 렌즈 종류/색상, 로고 적용 여부, 포장 방식, 예상 수량, 희망 납기를 입력한다. 잘 모르는 항목에는 쉬운 설명과 추천 선택지가 표시된다.
4. 참고할 제품 사진이나 디자인 파일을 첨부한다. 정확한 사양을 모르면 "상담 후 결정"을 선택할 수 있다.
5. 입력한 조건을 기준으로 AI가 예상 공장 EXW 가격 범위, Bridge Path 서비스 수수료 8%, 별도로 발생할 수 있는 운송·통관 비용 항목, 예상 제작기간을 보여준다. 확정 견적이 아니라 참고용 예상 범위임을 명확히 안내한다.
6. 회원가입을 강제하지 않고, 회사/브랜드명·담당자 이름·전화번호·이메일을 입력해 정식 견적 검토를 요청할 수 있다.
7. 요청이 접수되면 접수번호와 예상 답변 시간을 확인하고, 이메일/알림으로도 접수 내용을 받는다.
8. Bridge Path 담당자가 요청 내용을 검토하고(필요시 추가 질문), 중국 공장에 실제 조건을 확인해 정식 견적을 작성한다. 정식 견적에는 제품 제작비(EXW)·Bridge Path 서비스 수수료·예상 실비 항목이 구분되어 표시된다.
9. 이후 계정을 만들거나 간편 인증으로 마이페이지에서 정식 견적을 확인하고, 수정 요청이나 파일을 추가로 전달할 수 있다.
10. 정식 견적을 승인한 뒤, 계약서·발주서에 따라 계좌이체로 계약금·잔금을 지급하는 절차를 거친다 — 이 계약·입금 과정은 웹서비스 밖에서 진행된다(아래 "계약·결제 범위" 참고). 이후 제작이 시작되면, 마이페이지에서 샘플 준비 → 샘플 확인 → 생산 준비 → 생산 중 → 검수 → 출고 → 배송의 진행 상태를 확인한다. 중요한 상태 변경은 이메일/알림으로 받는다.
11. 최종적으로 중국 공장과 직접 소통하거나 운송·통관 과정을 일일이 처리하지 않고 자체 브랜드 선글라스를 받아 판매할 수 있다.

**이 여정에서 나온, 아직 확정하지 않고 열어두는 질문**:
- 가격 기준(환율 등 적용 시점) — 기존 Product Brief에서도 미확정 항목으로 남아있던 것과 동일
- 최소 주문수량(MOQ)
- 견적 답변 시간(정식 견적까지 예상 SLA)
- 제작 단계 명칭과 구성(샘플 준비/샘플 확인/생산 준비/생산 중/검수/출고/배송이 실제 운영 단계와 맞는지)

*(결제 조건은 아래 "계약·결제 범위"에서 확정했다 — 방식은 계좌이체, 비율·시점은 주문별로 다르게 정하는 것이 원칙이라 더 이상 열린 질문이 아니다.)*

**이 여정에서 드러난 두 번째 행위자**: 8번 단계에서 "Bridge Path 담당자"가 요청을 검토하고 공장에 확인해 정식 견적을 작성한다 — 이는 관리자/운영자 쪽 기능(견적 요청 검토, 정식 견적 작성·발송)이 필요하다는 뜻이며, 이번 PRD의 미확정 항목 중 "관리자 기능 최소 범위"와 직접 연결된다. 별도 UJ-2(관리자 관점)로 추후 구체화한다.

### UJ-2: 담당자의 견적 검토·정식 견적 작성 (승인됨)

> 전체 업무 흐름은 실제 의도와 대체로 일치한다고 확인받았다. MVP는 **전용 최소 관리자 화면을 포함**하는 방향으로 결정했다 — 아래 표와 FR-5에 반영.

**주인공**: 지은 — Bridge Path의 견적·무역 담당자. 고객 요청을 검토하고, 중국 제조업체·포워딩 파트너와 소통해 정식 견적을 만들어 회신하는 사람.

민수(UJ-1)가 선글라스 견적을 요청한 직후 상황이다.

1. 새 견적 요청이 들어왔다는 알림을 받는다.
2. 민수가 입력한 고객정보, 제품 사양, 첨부파일을 확인한다.
3. 사양이 불충분하면 민수에게 추가로 질문한다.
4. 확인된 사양과 수량을 중국 제조업체에 전달한다.
5. 공장으로부터 EXW 가격, MOQ, 샘플비, 금형비, 예상 제작기간을 확인받는다.
6. 필요하면 포워딩 파트너에게 운송 관련 조건을 확인한다.
7. 공장 EXW 가격과 Bridge Path 서비스 수수료 8%를 구분해서 계산한다.
8. 운송·통관 등 별도 실비와, 아직 변동 가능한 항목을 구분해 표시한다.
9. 이 내용을 종합해 정식 견적서를 작성한다.
10. 민수에게 정식 견적을 전달한다.
11. 민수의 수정 요청, 승인, 또는 보류 여부를 확인하고 상태를 기록한다.
12. 견적이 승인되면 샘플·생산 단계로 이어진다 *(이 뒷부분은 아직 논의하지 않은 "제작현황" 영역이라 여기서는 연결 지점만 표시)*.

**단계별로 웹서비스 안에서 필요한 최소 기능 vs 초기엔 수동으로 처리 가능한 업무를 구분해보면:**

| 단계 | 웹서비스 안에서 필요한 최소 기능 | 초기엔 수동 처리 가능 |
|---|---|---|
| 1. 신규 요청 알림 | FR-4.4의 이메일 알림으로 이미 충족 — 추가 기능 불필요 | — |
| 2. 고객정보·사양·첨부파일 확인 | **전용 최소 관리자 화면**에서 담당자가 로그인 후 조회 (FR-5) | 확인 후의 검토·판단 자체는 사람이 함 |
| 3. 추가 질문 | — | 전화·이메일로 직접 연락 |
| 4. 중국 제조업체에 전달 | — | 위챗·이메일 등 기존 방식으로 수동 |
| 5. 공장 조건 확인 | — | 완전히 오프라인 실무 |
| 6. 포워딩 파트너 확인 | — | 완전히 오프라인 실무 |
| 7. EXW·수수료 8% 계산 | (있으면 좋음) 계산을 도와주는 도구 — FR-3 고객용 계산 로직과 개념적으로 겹치는 부분이라 재사용 여지 있음 | 수기 계산도 가능 |
| 8. 실비·변동항목 표시 | (있으면 좋음) 견적서 템플릿 | 문서 도구로 수동 작성 가능 |
| 9. 정식 견적서 작성 | 완성된 파일(엑셀/PDF 등)을 해당 요청에 첨부하는 기능만 제공 (FR-5.7) | 견적서 자체의 작성·계산은 외부 문서 도구로 수동 |
| 10. 고객에게 견적 전달 | 발송 여부를 관리자 화면에 기록 (FR-5.8) | 실제 발송은 이메일 등 외부 수단으로 수동 |
| 11. 상태 기록 (수정요청/승인/보류) | 관리자 화면에서 처리상태 변경 (FR-5.5, 상태값 후보는 FR-5 하단 참고) | 상태 판단 자체(고객이 뭐라 답했는지 해석)는 사람이 함 |
| 12. 승인 후 샘플·생산 연결 | 아직 논의 전 — "제작현황" 주제에서 다룸 | — |

**확정된 MVP 최소 관리자 역량**은 아래 FR-5에 정리했다. 중국 공장·포워딩 파트너와의 소통(4~6번)은 MVP에서 전화·이메일·위챗 등 외부 수단으로 수동 처리하며, 서비스 내부 채팅이나 공장 계정은 이후 버전으로 미룬다.

### UJ-3: 고객 로그인·마이페이지 (2차 버전 — 초안, 검토 대기)

> **MVP에는 포함하지 않는다.** 고객용 로그인 없이도 MVP 여정(FR-1~4)은 완결된다 — 접수번호·요약 확인, 이메일을 통한 접수확인·정식견적서 수신까지가 MVP의 끝이다. 아래는 2차 버전을 위해 미리 기록해두는 장기 여정이다.

**주인공**: 민수 (UJ-1과 동일 인물). 며칠 뒤 지은(UJ-2)이 이메일로 정식 견적서를 보내왔다.

1. 민수는 이메일로 받은 정식 견적서를 확인하고, 나중에 다시 보거나 진행 상황을 확인하고 싶어서 Bridge Path 사이트에 다시 방문한다.
2. 계정을 만들거나 안전한 본인 인증을 거쳐 로그인한다 *(구체적 인증 방식은 Architecture 단계에서 결정)*.
3. 처음 비회원으로 제출했던 견적 요청이 본인 계정에 안전하게 연결된다 *(연결 방식 — 이메일 일치 확인 등 — 은 Architecture 단계에서 결정)*.
4. 마이페이지에서 본인이 요청한 견적 목록을 확인한다.
5. 특정 견적을 선택해 제출한 사양, 처리상태, 정식 견적서를 확인한다.
6. 정식 견적서 파일을 다운로드한다.
7. 수정하고 싶은 부분이 있으면 추가정보나 수정 요청을 제출한다.
8. 다른 고객의 견적이나 파일은 절대 보이지 않는다 — 본인 것만 조회된다.

### UJ-4: 제작·무역 진행현황 확인 (3차 버전 — 초안, 검토 대기)

> **MVP·2차 버전 모두 포함하지 않는다.** 견적 승인 이후 계약·결제·생산이 진행되는 동안 고객이 진행 상황을 확인하는 장기 여정이다.

**주인공**: 민수. 정식 견적을 승인하고 계약·결제까지 마친 이후.

1. 마이페이지에 로그인해서 승인된 견적의 진행 상황을 확인한다.
2. 진행 상황은 샘플 준비 → 샘플 확인 및 수정 → 생산 준비 → 생산 중 → 검수 → 출고 → 배송 등의 단계로 표시된다 *(정확한 단계 명칭·구성은 실제 운영 프로세스를 확인한 뒤 확정)*.
3. 각 단계에 관련 사진이나 파일이 첨부되어 있어 시각적으로 확인할 수 있다.
4. 중요한 상태 변경(예: 생산 시작, 출고 등)마다 이메일이나 알림으로 통지받는다.
5. 최종적으로 배송 완료를 확인하고 제품을 수령한다.

**UJ-3·UJ-4 공통 원칙**:
- 접수번호만 입력해서 다른 고객의 견적을 조회할 수 있어서는 안 된다.
- 고객은 본인의 견적과 파일만 볼 수 있어야 한다.
- 고객에게 보여주는 상태와 내부 관리자 상태(FR-5.5)는 다를 수 있다.
- 로그인 방식과 인증 기술은 Architecture 단계에서 결정한다.

## MVP Scope — 기능별 결정

UJ-1을 따라가며 기능 단위로 하나씩 결정한다. 각 기능은 고객 관점 필요성, 없으면 견적 요청이 불가능한지, 구현 난이도, 1차/이후 버전 여부를 근거로 판단한다.

### FR-1: 견적 입력 폼 (제품 사양 입력) — **MVP**

고객이 원하는 제품의 사양을 입력해 의뢰를 구체화하는 폼. 여정 3번 단계에 해당.

- **FR-1.1** 정식 문의 제출을 위한 최소 필수정보: 제품 종류(또는 카테고리), 예상 수량(정확한 수치를 모르면 "수량 미정"으로 표시 가능), 요청 내용에 대한 간단한 설명. 이 세 가지만으로도 문의가 가능해야 한다 — 제조 지식이 부족한 고객도 문의할 수 있어야 한다. *(카테고리 4는 예상 수량의 필수 여부가 다르다 — FR-1.6 참고. 이 최소정보는 AI 예상가격 표시에 필요한 정보와 다르다 — FR-3.14 참고)*
- **FR-1.2** 소재, 색상, 렌즈 사양, 로고, 포장, 희망 납기, 세부 치수 등 제품별 세부 사양은 제품 유형(아이웨어/신발/골프용품/기타 — FR-9 참고)에 맞게 제공하되, 전부를 필수 입력으로 강제하지 않는다.
- **FR-1.3** 세부 항목에는 "잘 모르겠음", "추천받고 싶음", "담당자와 상담 후 결정" 같은 선택지를 제공한다.
- **FR-1.4** 입력 항목 옆에는 초보 고객도 이해할 수 있는 쉬운 설명이나 예시를 제공한다.
- **FR-1.5** 공통 고객정보(회사/브랜드명, 담당자, 연락처 등)와 제품별 사양정보를 구조적으로 구분한다 — 아이웨어·신발·골프용품·기타는 제품 특성이 다르기 때문이다.

- **FR-1.6** 카테고리 4(기타 제품·국내외 공장 매칭 및 컨설팅)는 먼저 **지원 유형**을 선택하게 한다: "제조·생산 의뢰" / "제품 소싱·공장 매칭 상담" / "어떤 방식이 맞는지 상담 필요". 화면 전체를 유형별로 분리하지 않고, **하나의 폼 안에서** 지원 유형에 따라 예상 수량의 필수 여부와 안내 문구만 달라진다:
  - 제조·생산 의뢰 → 예상 수량 필수 (단, "아직 모름 / 상담 후 결정" 선택 가능)
  - 제품 소싱·공장 매칭 상담 → 예상 수량 선택 입력
  - 어떤 방식이 맞는지 상담 필요 → 예상 수량 선택 입력
  
  지원 유형과 무관한 공통 필수정보는 만들거나 찾으려는 제품의 종류·이름, 요청 내용에 대한 간단한 설명, 고객 연락처 등 기본정보(FR-4.2)다. 첨부파일(FR-2)은 모든 지원 유형에서 선택 사항이다.

**[OPEN]** AI 예상견적을 계산하기 위해 필요한 정보와, 담당자에게 정식 상담을 요청하기 위한 필수정보는 서로 다를 수 있다. 세부 기준은 AI 예상견적 기능을 다룰 때 별도로 결정한다.

**판단 근거**: 없으면 "의뢰를 넣는다"는 행위 자체가 성립하지 않는 여정의 진입점. 기존 `sunglasses-estimate.html` 등에 유사 폼이 있어 항목 보강 수준의 난이도. 데이터를 실제로 저장·전송하는 부분은 별개 기능(뒤에서 논의).

### FR-2: 참고 이미지·디자인 파일 첨부 (선택 항목) — **MVP**

고객이 원하는 제품의 참고 사진이나 디자인 파일을 첨부하는 기능. 여정 4번 단계에 해당.

- **FR-2.1** 파일 첨부는 견적 문의의 필수조건이 아니다 — FR-1.1의 최소 필수정보만으로도 문의를 제출할 수 있어야 한다.
- **FR-2.2** 첨부 파일은 견적 요청 데이터와 연결되어, Bridge Path 담당자가 안전하게 확인할 수 있어야 한다. 브라우저 화면에 파일명만 표시하거나 `console.log`로 끝나는 것은 기능 완료로 보지 않는다 — 실제 저장·전송까지 포함한다.
- **FR-2.3** 고객은 선택한 파일의 이름을 확인하고, 잘못 선택한 파일을 삭제하거나 교체할 수 있다.
- **FR-2.4** 업로드 실패 시 이유와 재시도 방법을 쉽게 안내한다. 선택 기능이므로, 파일 업로드 실패가 이미 입력한 나머지 문의 내용을 사라지게 해서는 안 된다.
- **FR-2.5** 아이웨어, 신발, 골프용품, 기타 제품·공장 매칭 문의(FR-9) 전체에서 공통으로 사용할 수 있어야 한다.
- **FR-2.6** 허용 형식은 JPG, JPEG, PNG, WEBP, PDF다. 파일당 최대 10MB, 최대 5개, 견적 요청 1건당 전체 첨부 용량은 최대 30MB다. AI·PSD·EPS 등 디자인 원본 파일과 압축파일(zip 등)은 MVP 업로드 대상에서 제외한다 — 필요한 경우 접수 후 담당자와 협의해 이메일 등으로 별도 전달하도록 안내한다.
- **FR-2.7** 파일 검증은 확장자 이름만으로 판단하지 않는다. 실제 파일 형식과 MIME 유형을 서버에서 검증해, 실행파일이나 허용되지 않은 형식은 파일명을 바꿔도 업로드할 수 없어야 한다.
- **FR-2.8** 저장 시 파일명은 안전한 내부 식별자로 변경한다. 원본 파일명은 화면 표시용 정보로 별도 보관한다.
- **FR-2.9** 첨부파일은 관리자 권한이 있는 사용자만 열람·다운로드할 수 있다. 공개 URL을 아는 것만으로 파일을 열 수 있는 방식은 허용하지 않는다.
- **FR-2.10** 파일별 업로드 성공·실패 상태를 고객에게 명확히 표시한다. 허용되지 않은 형식, 파일당 용량 초과, 전체 용량 초과는 각각 이해하기 쉬운 문구로 구분해서 안내한다.
- **FR-2.11** 같은 파일을 실수로 여러 번 첨부한 경우, 중복 여부를 고객이 확인할 수 있게 표시한다.

**[NFR — 보안]** 고객의 디자인·로고는 사업상 중요한 자료일 수 있으므로, 허가받지 않은 사람이 접근하지 못하도록 해야 한다. PDF도 잠재적으로 위험할 수 있어, 악성 파일 검사 방식과 저장소 구성은 Architecture 단계에서 검토할 보안 요구사항으로 남긴다. 공개 URL만으로 파일을 열 수 있는 방식은 허용하지 않는다(FR-2.9).

**[OPEN]** 스마트폰에서 많이 쓰이는 HEIC/HEIF는 MVP 허용 형식에 포함하지 않는다. 실제 브라우저·저장·미리보기 지원 가능성을 Architecture 단계에서 확인한 뒤 추가 여부를 결정한다.

**판단 근거**: 없어도 FR-1의 최소 필수정보로 문의는 성립하므로 선택 항목. 단, "파일 선택 UI"는 이미 존재하지만 "실제 저장·전송·담당자 열람"까지 포함하면 구현 난이도는 **중간 이상**이다(기존 코드는 화면 표시만 하고 실제로는 아무 데도 전달되지 않는 상태이기 때문).

### FR-3: AI 사전 가격안내 (참고용 예상가격 범위) — **MVP 조건부**

애초 "규칙 기반 계산기"로 구상했던 이 기능은, 실제 사업모델 검토와 경쟁 서비스(sinple.co.kr) 사례 분석을 거쳐 아래 형태로 재정의됐다. **"AI 견적"이나 "확정 견적"이 아니라, 승인된 기준 단가표를 바탕으로 한 참고용 예상가격 범위 안내다.** 여정 5번 단계에 해당한다.

**MVP의 안전한 기본 동작 (요약)**: 조건을 충족하면 내부 승인 기준가격을 표시한다. 조건이 부족하면 숫자를 생성하지 않고 상담으로 연결한다. 플랫폼 참고가격(FR-3.13의 기술검증)은 검증이 성공한 경우에만 별도로 추가 표시된다.

**역할 분담 — AI는 가격을 만들지 않는다:**
- **FR-3.1** AI(이미지·설명 분석)는 제품 유형 분류, 눈에 보이는 특징 후보 추출, 고객 확인 질문 생성에만 사용한다. LLM 일반지식이나 공개 시장정보도 가격의 직접 근거로 쓰지 않고, 분류·설명·질문·사양 정리를 돕는 용도로만 사용한다.
- **FR-3.2** 실제 가격 숫자는 Bridge Path 담당자가 승인한 **품목별 기준 단가표**에서만 나온다. 표에 없는 조합은 숫자를 만들어내지 않는다.
- **FR-3.6** AI가 이미지에서 추정한 특징(소재·구조 등)은 가격 계산에 바로 반영하지 않고, 고객에게 "이렇게 보이는데 맞나요?" 확인 질문으로 제시한다.
- **FR-3.14** AI 예상가격을 표시하려면 정식 견적 요청의 최소정보(FR-1.1: 품목/카테고리, 예상 수량 또는 수량 미정, 간단한 설명)만으로는 부족하다 — 이 둘은 서로 다른 최소정보 집합이다. AI 예상가격 표시에는 추가로 다음이 필요하다: (1) AI 예상가격 지원 대상에 해당하는 세부 품목(기준표의 표준 사양과 매칭되는 단위), (2) 정확한 예상 수량(미정 불가 — FR-3.5의 예외 3번과 연결), (3) 표준 사양 일치 여부에 대한 고객 확인, (4) 품목별로 정의된 핵심 옵션(가격에 큰 영향을 주는 항목만).
- **FR-3.15** 가격을 표시하기 전에, 해당 세부 품목의 표준 사양을 고객이 이해하기 쉽게 보여주고 다음 중 하나를 선택하게 한다: (1) "이 표준 사양으로 예상가격 확인" (2) "일부 조건이 다름" (3) "잘 모르겠음·상담 필요". (1)을 선택하고 핵심 옵션까지 입력한 경우에만 내부 기준가격을 적용한다. (2) 또는 (3)을 선택하면 가격을 표시하지 않고 담당자 상담으로 연결한다(FR-3.5). 품목별 핵심 옵션은 모든 품목에 동일하게 만들지 않고, 기준표 준비 절차에서 품목별로 결정한다 — 예를 들어 소재·구조·로고·포장·금형 여부 중 실제 단가에 큰 영향을 주는 항목만 최소한으로 받는다.

**계산 방식:**
- **FR-3.3** 고객이 입력한 정확한 예상 수량이 속하는 수량 구간의 승인된 단가 범위를 찾아, 그 범위 × 정확한 수량으로 총 예상비용 범위를 계산한다(가장 가까운 구간으로 근사하지 않는다). 예: 100~299개 구간의 단가범위가 10,000~12,000원이고 입력 수량이 250개면, 총 예상비용은 2,500,000~3,000,000원이다.
- **FR-3.4** 수량 구간은 빈틈이나 중복이 없도록 설계한다(예: 100~299 / 300~999 / 1,000~2,999). 상한이 없는 구간("1,000개 이상")은 실제 공장 자료로 그 범위까지 검증된 경우에만 쓴다 — 그렇지 않으면 검증된 상한까지만 두고 그 이상은 상담으로 연결한다.
- **FR-3.5** 다음 5가지 경우에는 가장 가까운 구간 가격을 임의로 적용하지 않고 상담으로 연결한다: (1) 해당 품목의 최소주문수량(MOQ)보다 적은 경우, (2) 기준표가 검증한 최대 수량 범위를 초과한 경우, (3) 고객이 정확한 수량을 모르고 "미정"을 선택한 경우, (4) 고객 사양이 기준가격의 표준 사양과 크게 다른 경우, (5) 해당 수량 구간의 기준가격이 없거나 유효기간이 지난 경우.

**표시 방식:**
- **FR-3.7** 예상가격 범위에는 생성일과 참고 유효기간을 함께 표시한다.
- **FR-3.8** AI 예상가격을 제공할 수 있는 품목에는 별도 표시(배지 등)를 제공하고, 지원하지 않는 품목은 일반 견적·상담 요청으로 연결한다. 정확한 배지 문구·디자인은 UX 단계에서 결정한다.
- **FR-3.9** 예상 공장 EXW 가격 범위, Bridge Path 서비스 수수료 8%(EXW와 별도 항목), 운송·통관 등 실비는 "실제 조건에 따라 별도 발생"함을 안내한다. 가격 범위에 포함된 항목과 제외된 항목을 명시하고, EXW 기준인지 다른 가격조건인지 명확히 표시한다.
- **FR-3.10** 예상 제작기간을 제품 유형별 대략적 범위로 함께 안내한다.
- **FR-3.11** 결과 화면에서 정식 견적 요청(FR-4)으로 바로 이동할 수 있게 한다.
- **FR-3.12** AI 분석 결과, 사용한 입력정보, 기준자료 버전과 생성 시점을 기록해 담당자가 나중에 확인할 수 있게 한다(FR-5).

**FR-3.13 (가격 근거 3종 분리)**: 화면에 표시되는 가격은 반드시 다음 세 가지 근거 중 하나로 명확히 표시되며, 서로 다른 근거의 가격을 하나의 평균값으로 합치지 않는다.
1. 플랫폼 유사상품 참고가격 (있는 경우 — 아래 기술검증 과제 참고)
2. Bridge Path가 승인한 내부 기준가격 (FR-3.2)
3. 담당자가 공장에 확인한 정식견적 (FR-5)

**[기술검증 과제 — Architecture 이전 또는 초기 수행, MVP 확정 요구사항 아님]** 1688·Alibaba.com 같은 플랫폼의 이미지 검색·유사상품 가격 API를 AI 사전 가격안내의 **보조 근거**로 쓸 수 있는지 검증한다.

*확인되지 않은 사항*: 1688/Alibaba.com이 Bridge Path 용도로 쓸 수 있는 공식 API를 제공하는지 / API 신청에 사업자·파트너 자격이 필요한지 / MOQ·수량구간별 가격이 응답에 포함되는지 / 검색결과·가격을 재가공해 고객에게 표시하는 것이 이용약관상 허용되는지 / API 비용과 호출 제한 / 한국에서 안정적으로 쓸 수 있는지.

*기술검증 성공 기준(6가지)*: (1) 공식적으로 사용 가능한 API 확보 (2) 이미지 또는 제품조건으로 유사상품 검색 가능 (3) 상품가격·통화·단위·MOQ·가격구간·판매자정보 확보 가능 (4) 이용약관상 가격분석 및 고객 대상 표시 가능 (5) 같은 테스트 이미지로 반복했을 때 비교 가능한 결과 확보 (6) 명백히 관련 없는 상품과 비정상 가격을 필터링할 수 있음.

*채택되는 경우 반드시 지켜야 할 사용 원칙*: 표시가격의 단순 평균을 OEM 공장 EXW 가격으로 간주하지 않는다(완제품 도매가·MOQ별 가격·샘플가격·홍보성 최저가·유통업체 가격·옵션 제외 가격 등이 섞일 수 있음) / 이미지 유사도·제품 속성이 낮은 결과 제외 / 제조업체와 유통업체 가능성 구분 / 고객 수량과 맞지 않는 MOQ·가격구간 제외 / 샘플가격, 비정상적으로 낮거나 높은 가격, 단위가 다른 상품 제외 / 통화·단위 통일 / 단순 평균이 아니라 중앙값과 검증된 가격범위 산출 / 검색 플랫폼·검색일시·상품 수·MOQ·포함/제외 기준을 함께 표시 / 가격 근거가 부족하면 숫자를 표시하지 않고 상담으로 연결.

*대안(API 미확보 또는 데이터 신뢰성이 낮은 경우)*: 이 기능은 제외하고, 고객 이미지를 바탕으로 AI가 사양을 정리(FR-3.1)한 뒤 담당자 상담으로 연결하는 방식으로 대체한다.

*이 경로(경로 B)가 채택될 경우의 최소정보*: 이미지 기반 플랫폼 검색을 실행하려면 이미지 첨부가 필수다(첨부하지 않으면 이 경로는 자동으로 건너뛰고 내부 기준가격 경로로만 진행). 정확한 수량은 MOQ·가격구간 필터링을 위해 필수다. AI가 이미지에서 추출한 제품 특징은 고객이 확인하거나 수정한다(FR-3.6). 검색 결과(플랫폼 참고가격)는 내부 기준가격과 합쳐 하나의 평균으로 만들지 않고, "플랫폼 유사상품 참고가격"과 "Bridge Path 내부 기준 예상가격"을 별도로 표시한다(FR-3.13). API 기술검증이 실패하면 경로 B는 비활성화하고, 경로 A(내부 기준가격) 및 상담 연결만 사용한다. **희망 제작지역(중국/국내 등)은 경로 B의 필수 입력으로 지금 확정하지 않는다** — 1688 기반 참고가격이라면 결과 자체가 중국 플랫폼 기준이라는 점만 명시하면 되고, 국내·다른 국가 가격 비교는 별도의 신뢰 가능한 데이터 출처가 확보됐을 때 확장한다.

**경쟁 서비스(sinple.co.kr)와의 관계**: sinple.co.kr은 참고자료로만 사용했다 — 그 가격·MOQ·유효기간 수치를 Bridge Path 기준으로 그대로 복사하지 않는다. 다만 sinple.co.kr의 요청자 정보를 공장에 직접 제공하는 매칭 방식은 Bridge Path 모델과 다르다는 점은 명확히 한다 — Bridge Path는 담당자가 중개하는 구조를 유지하며 고객 정보를 공장에 직접 노출하지 않는다(FR-4, FR-5의 기존 원칙과 일치).

**기준표 준비 절차** (Bridge Path의 운영 작업이며 PRD 범위 밖이지만, 절차는 기록해둔다):
1. 실제 파트너 공장에 해당 품목의 MOQ 확인
2. 표준 사양 정의
3. 의미 있는 수량 구간 확인
4. 구간별 EXW 단가 또는 단가 범위 확인
5. 견적 통화·견적일·유효기간·포함/제외 항목 기록
6. 가능하다면 기존 거래자료 또는 추가 공장 견적과 비교
7. Bridge Path 담당자가 고객 노출 가능 여부를 승인

**[OPEN]** 단가 범위를 만드는 데 공장 한 곳의 견적 하나로 충분한지, 복수 공장 견적이나 과거 거래자료 비교가 필요한지.
**[OPEN]** 선글라스·골프화·나무 골프티는 품목별 MOQ와 핵심 가격 변수가 다르므로, 동일한 수량 구간을 일괄 적용하지 않고 품목별로 각각 설계한다 — 구체적인 구간·표준 사양은 품목별로 별도 확정한다.
**[가설, 확정 아님]** "표준 사양 1종 × 수량 구간 3개, 총 9개의 단가 범위로 시작 가능하다"는 논의 중 나온 최소 규모 참고 가설일 뿐, 확정된 요구사항이 아니다. 실제 최소 규모는 위 준비 절차를 거쳐 품목별로 다르게 정해질 수 있다.
**[OPEN]** AI 예상가격의 정확한 유효기간(7일/14일/30일 등) — 기준가격 갱신 주기와 실제 공장 견적의 유효기간을 확인한 뒤 결정한다.
**[OPEN]** 제품별 기준가·가격표의 실제 수치와 산정 근거 — Bridge Path 운영진이 준비해야 하는 데이터로, 이 PRD의 범위 밖이다.
**[OPEN]** 예상 제작기간의 제품별 구체적 범위 기준.
**[OPEN]** AI 예상가격 표시 흐름의 구조(FR-3.14, FR-3.15)는 확정했지만, 품목별 "핵심 옵션" 목록과 화면 문구는 기준표 준비 절차와 API 기술검증(FR-3.13) 결과가 나온 뒤에 확정한다.

**판단 근거**: 담당자가 준비하는 기준표가 선행되어야 동작하므로 MVP 조건부. AI가 분류·질문 생성에만 관여하고 가격 숫자를 직접 만들지 않기 때문에, LLM이 일반지식만으로 가격을 생성하는 방식보다 신뢰 위험이 낮다.

### FR-4: 정식 견적 요청 제출 및 접수 확인 — **MVP**

고객이 입력한 내용을 실제로 Bridge Path에 전달하고, 접수를 확인받는 기능. 여정 6~7번 단계에 해당하며, 지금 사이트가 `console.log`로 그치는 것을 실제 전달·저장으로 바꾸는 핵심 지점이다.

- **FR-4.1** 고객은 회원가입 없이도 정식 견적 요청을 제출할 수 있다.
- **FR-4.2** 고객은 먼저 **고객 유형**을 선택한다: "개인·창업 준비 중" / "사업자·브랜드 운영 중". 완전히 다른 폼을 쓰지 않고, 고객 유형에 따라 회사명·브랜드명의 필수 여부만 달라지는 단순한 조건부 입력으로 구성한다.
  - **개인·창업 준비 중**: 이름 필수, 회사명·브랜드명은 선택(없어도 견적 요청 가능), 사업자등록번호는 MVP에서 요구하지 않는다.
  - **사업자·브랜드 운영 중**: 담당자 이름 필수, 회사명 또는 브랜드명 필수, 사업자등록번호는 MVP에서 요구하지 않는다.
  - 공통 필수: 이메일 또는 전화번호 등 회신 가능한 연락처, 개인정보 수집·이용 동의.
  - 화면 안내에서는 "개인 고객"이 일반 소비자의 소량 구매나 완제품 쇼핑으로 오해되지 않도록, 창업 준비 또는 제품 제작·소싱 문의를 위한 구분임을 명확히 한다.
  - 고객 유형 값은 접수 데이터에 저장되어 관리자 목록·상세 화면에서 확인할 수 있어야 한다 (FR-5.2, FR-5.3).
- **FR-4.3** 제출된 제품 사양, 고객정보, 첨부파일(FR-2)은 화면에서 사라지지 않고 Bridge Path가 나중에 다시 확인할 수 있도록 안전하게 저장된다. 저장 기술은 Architecture 단계에서 결정한다.
- **FR-4.4** 담당자에게 보내는 이메일은 새 요청을 알려주는 **알림 수단**이다. 이메일 발송이 실패하더라도 저장된 견적 요청까지 사라져서는 안 된다.
- **FR-4.5** 정상 접수 후 고객에게 고유한 접수번호, 접수 일시, 제출 내용 요약을 보여준다.
- **FR-4.6** 중복 클릭이나 네트워크 재시도로 동일한 요청이 여러 번 접수되는 문제를 방지한다.
- **FR-4.7** 필수정보 누락, 첨부 실패, 저장 실패 등으로 접수가 완료되지 않았다면 성공 메시지나 접수번호를 보여주지 않는다. 고객에게 실패 이유와 재시도 방법을 안내한다.
- **FR-4.8** 고객이 접수 완료 내용을 이메일 등으로 받을 수 있는 기능을 포함한다. 발송 방식과 서비스는 Architecture 단계에서 결정한다.

**[NFR — 보안]** 접수번호만으로 다른 고객의 요청을 조회할 수 있는 구조가 되어서는 안 된다.

**[OPEN]** 예상 답변 시간(SLA)은 운영 기준이 아직 정해지지 않아 임의로 약속하지 않는다. 기준이 확정되기 전에는 "담당자 확인 후 연락드리겠습니다" 식으로 표시할 수 있다.

**판단 근거**: 이게 없으면 FR-1~3에서 만든 모든 것이 실제로는 아무 데도 전달되지 않는 화면일 뿐이다 — 서비스가 성립하는 핵심 지점. 지금 정적 사이트에 실제 저장·전달 경로가 필요해지는 지점이라 난이도는 중간이며, 구체적 구현 방식은 Architecture 단계로 넘긴다.

### FR-5: 관리자 로그인 및 최소 관리자 화면 — **MVP** (범위 제한)

Bridge Path 담당자가 안전하게 로그인해서 견적 요청을 확인하고 처리하는 전용 화면. UJ-2 전체에 해당하며, 고객용 로그인·마이페이지(아직 미정)와는 별개로 담당자 쪽은 MVP에 포함하기로 결정했다.

- **FR-5.1** 관리자 로그인 (담당자만 접근 가능한 안전한 인증)
- **FR-5.2** 견적 요청 목록 조회 (고객 유형 — 개인·창업 준비 중 / 사업자·브랜드 운영 중 — 을 함께 표시, FR-4.2)
- **FR-5.3** 요청별 고객정보와 제품 사양 상세 조회 (카테고리 4는 지원 유형 — 제조·생산 의뢰 / 소싱·매칭 상담 / 상담 필요 — 을 함께 보여준다, FR-1.6)
- **FR-5.4** 첨부파일(FR-2) 안전하게 확인 및 다운로드 — 관리자 권한이 있는 사용자만 접근 가능 (FR-2.9)
- **FR-5.5** 처리상태 변경 (상태값 10개 확정 — 아래 참고). 보류·종결·취소로 변경할 때는 내부 메모(FR-5.6)에 사유를 기록하도록 안내한다 — MVP에서는 사유를 별도의 분류값으로 만들지 않는다.
- **FR-5.6** 담당자 내부 메모 기록
- **FR-5.7** 외부에서 작성한 정식 견적서 파일(엑셀/PDF 등)을 해당 요청에 첨부
- **FR-5.8** 고객에게 견적을 발송했는지 여부 기록 (실제 발송은 이메일 등 외부 수단으로 수동 처리)

**MVP에서 명시적으로 제외**: 견적 요청 삭제, 통계 기능, 여러 관리자 권한(역할 구분), 공장·포워더 전용 계정, 서비스 내부 채팅, 자동 견적서 생성. 모두 이후 버전 후보.

**상태값 (확정, 10개)** — 이 상태는 "견적 문의 처리 상태"이며, 실제 제작·무역 진행 상태(FR-7, 3차 버전)와는 별개의 개념이다. MVP에는 고객용 마이페이지가 없으므로 이 상태값은 우선 **내부 관리용**으로만 쓰인다. 고객에게는 필요한 경우 접수 완료·정식견적 발송 등 주요 사실만 이메일로 안내한다. 2차 버전(FR-6)에서 고객에게 공개할 상태는 이 내부 상태와 별도로 단순화해서 다시 설계한다.

| 신규 접수 | 고객의 요청이 정상적으로 저장됐지만 담당자가 아직 검토하지 않은 상태 |
| 정보 확인 중 | 담당자가 고객의 요청 내용과 첨부파일을 검토하는 상태 |
| 추가정보 요청 | 견적에 필요한 정보가 부족하여 고객에게 추가 내용을 요청한 상태 |
| 공장 견적 확인 중 | 필요한 정보를 바탕으로 공장 및 관련 파트너에게 가격·조건을 확인하는 상태 |
| 정식견적 발송 | 고객에게 정식견적서를 발송한 상태 |
| 고객 검토 중 | 견적 발송 후 고객의 답변이나 결정을 기다리는 상태 |
| 진행 확정 | 고객이 정식견적을 승인하여 이후 계약·입금 절차로 넘어가는 상태 *(내부적으로는 "고객의 정식견적 승인"을 의미 — "승인"이라는 명칭은 누가 무엇을 승인했는지 모호할 수 있어 "진행 확정"으로 표현)* |
| 보류 | 고객 또는 담당자 사정으로 일시적으로 진행을 멈춘 상태 |
| 종결 | 견적 문의 업무가 정상적으로 마무리되었거나 더 이상 후속 작업이 필요하지 않은 상태 *("완료"라는 명칭은 생산·배송까지 끝난 것으로 오해될 수 있어 "종결"로 표현)* |
| 취소 | 고객의 취소 요청 또는 진행 불가능 등의 사유로 의뢰가 취소된 상태 |

**[NFR — 감사 이력]** 상태를 변경할 때마다 다음 네 가지를 기록한다: 변경 전 상태, 변경 후 상태, 변경한 관리자, 변경 일시. 정식 견적서 첨부(FR-5.7) 등 다른 관리자 작업에도 동일한 최소 이력 원칙을 적용한다. 구체적인 기술 구현은 Architecture 단계에서 결정한다.

**판단 근거**: UJ-2에서 담당자의 업무(요청 확인 → 공장 문의 → 정식 견적 작성·회신) 자체는 MVP 필수임이 확인됨. 다만 공장·포워딩 소통(전화/이메일/위챗)과 견적서 작성(외부 문서)은 MVP에서 수동으로 처리하고, 서비스 안에는 "저장된 데이터 확인 + 최소 상태/메모 관리 + 완성 문서 첨부"까지만 최소 범위로 둔다.

### FR-8: 홈페이지 신뢰 형성 콘텐츠 — **MVP**

방문자가 첫 화면에서 Bridge Path가 무엇을 하는 회사인지 정직하게 이해하고, 견적 요청으로 자연스럽게 이어지도록 하는 콘텐츠. 여정 1~2번 단계에 해당. 새 인터랙티브 기능이 아니라 기존 `index.html` 콘텐츠를 사실에 맞게 보강하는 성격이다. **디자인과 최종 카피 문장은 이 단계에서 확정하지 않고 UX·디자인 단계로 남긴다.**

- **FR-8.1** 중국 제조업체 및 현지 포워딩 파트너 네트워크를 기반으로 한 소싱·제작·무역 지원 서비스임을 안내한다. "실거래 경험이 있는 중국 제조업체와 현지 포워딩 파트너 네트워크를 기반으로 제품 제작과 수입 과정을 지원한다"처럼 긍정적으로 표현하되, 공장을 직접 소유·제조하는 회사로 오해할 수 있는 표현은 사용하지 않는다.
- **FR-8.2** 각 카테고리의 검증된 레퍼런스(선글라스, 골프화, 나무 골프티, 화장품·고춧가루 유통 경험 — FR-9 참고)를 과장 없이 안내하며, 카테고리가 받는 넓은 범위와 혼동되지 않도록 구분해서 표현한다.
- **FR-8.3** 사양 정리 → 공장 소통 → 제작 관리 → 운송·수입까지 이어지는 업무 흐름 개요를 안내한다.
- **FR-8.4** 홈페이지에는 정확한 수수료 수치(8%)를 공개하지 않고, "투명한 비용 구조"와 "운송·통관 등 실제 발생 비용은 별도"라는 원칙만 안내한다. 정확한 서비스 수수료 8%는 AI 예상가격(FR-3)·정식견적(FR-5) 단계에서 EXW 공장가격과 분리해 명확히 표시한다.
- **FR-8.5** AI 예상가격(참고용 범위)과 담당자가 확인한 정식견적의 차이를 명확히 설명한다.
- **FR-8.6** 확인되지 않은 공장 수, 생산실적, 고객 수, 성공률 등의 수치는 사용하지 않는다. 모든 품목의 공장 네트워크를 이미 확보한 것처럼 표현하지 않는다 — 콘텐츠 작성 시 지켜야 할 과장 금지 원칙이다.
- **FR-8.7** 견적 요청 화면으로 쉽게 이동할 수 있는 CTA(버튼 등)를 포함한다.

**판단 근거**: 견적 입력 폼(FR-1) 자체는 이 콘텐츠 없이도 동작하지만, 신뢰 없이는 방문자가 개인정보를 입력할 가능성이 낮아 사업적으로는 사실상 필수다. 콘텐츠 보강 수준이라 구현 난이도는 낮다.

### FR-9: 제품 카테고리 구조 — **MVP**

기존 4개 카테고리(선글라스/신발/골프용품/기타)를 유지하되, **"핵심 상품만 좁게 취급"이 아니라 "넓은 범위를 받되 실거래 경험이 있는 품목을 대표 레퍼런스로 강조"하는 방향**으로 재편한다. 이 결정은 FR-1(견적 입력 폼), FR-2(첨부파일), FR-8(홈페이지 콘텐츠)의 제품 유형 구성에 그대로 반영된다.

**핵심 원칙 — 두 개념을 분리해서 표현한다:**
- **카테고리 범위(Scope)**: 고객에게 어떤 제품의 문의를 받을 것인지 — 넓게 정의됨
- **검증된 레퍼런스(Reference)**: Bridge Path가 실제 경험을 근거로 공개적으로 강조할 수 있는 품목 — 좁게, 사실에 근거해서만

이 둘을 혼동해서 표현하면 안 된다 — 예를 들어 "아이웨어를 전부 직접 제조해봤다"처럼 범위를 레퍼런스인 것처럼 말하지 않는다.

| 카테고리 | 범위 (받는 문의) | 검증된 레퍼런스 (강조 가능한 실거래 경험) |
|---|---|---|
| **1. 아이웨어** | 선글라스뿐 아니라 안경테 등 아이웨어 전반 | 선글라스 |
| **2. 신발** | 골프화뿐 아니라 운동화, 구두 등 신발 전반 | 골프화 |
| **3. 골프용품** | 나무 골프티, 골프 모자, 골프 항공커버, 골프백, 골프장갑, 골프채 헤드커버, 기타 골프 액세서리·용품 | 나무 골프티 *(별도의 최상위 카테고리로 분리하지 않는다)* |
| **4. 기타 제품·국내외 공장 매칭 및 컨설팅** | 화장품, 식품 및 식품 유통 관련 제품, 패션·생활용품, 기타 국내외 제조·소싱이 필요한 제품 | 화장품 유통 경험 + 관련 사업 자격 보유(공식 명칭은 서류로 확인하기 전까지 확정 표기하지 않음), 고춧가루 유통 경험 |

**카테고리 4(기타)의 성격**: 단순 "기타 OEM/ODM 문의"가 아니라, 아이웨어·신발·골프용품 외의 다양한 제품에 대해 제조 상담, 국내외 공장 탐색·매칭, 제품 소싱 및 관련 컨설팅을 폭넓게 받는 문의 창구다. 다만 모든 품목의 제작이나 공장 연결을 보장하는 것은 아니며, 접수 후 제품 조건과 대응 가능성을 담당자가 검토한다(자세한 안내 취지는 FR-10.6 참고). 화장품·식품 유통 경험은 이 역량의 근거이지, 직접 제조 경험이 아니다.

**과장 금지 (FR-8.6과 연결)**:
- 화장품을 직접 제조한 경험이 있는 것처럼 표현하지 않는다.
- 모든 품목의 공장 네트워크를 이미 확보한 것처럼 표현하지 않는다.
- 관련 사업 자격의 공식 명칭은 실제 등록증·사업자 서류로 확인되기 전까지 "관련 사업 자격 보유(공식 명칭 확인 필요)"로만 기록한다.

**이번 결정으로 업데이트된 기존 FR**: FR-1.2·FR-1.5의 제품 유형은 (아이웨어/신발/골프용품/기타)로, FR-2.5의 적용 범위도 동일하게 갱신했다. FR-8.2는 카테고리별 검증된 레퍼런스를 안내하도록 갱신했다.

**[OPEN]** 관련 사업 자격의 정확한 공식 명칭 — 서류 확인 필요.

**해결됨**: 카테고리 4의 입력 항목 구성은 FR-1.6(지원 유형 선택 + 예상 수량 필수 여부 분기)으로 결정했다.

**판단 근거**: 카테고리 구조는 FR-1의 "제품 유형" 선택지, FR-8의 홈페이지 콘텐츠 구성에 직접 영향을 주는 기초 데이터라 MVP 필수. 구체적 페이지 구성·카피·디자인은 확정하지 않는다.

### FR-10: 견적 요청으로 연결되는 진입 흐름 — **MVP**

방문자가 홈페이지(FR-8)에서 카테고리(FR-9)를 확인한 뒤, 자신에게 맞는 견적·상담 요청 폼(FR-1)으로 자연스럽게 이동하는 흐름. 기존 코드의 카테고리 허브 구조를 새 카테고리 체계에 맞게 잇는 역할이다.

- **FR-10.1** 홈페이지에서 카테고리 선택 화면 또는 견적 요청 흐름으로 이동할 수 있는 명확한 진입점을 제공한다 (FR-8.7과 연결).
- **FR-10.2** 아이웨어, 신발, 골프용품, 기타 제품·국내외 공장 매칭 및 컨설팅의 네 가지 선택지를 제공한다 (FR-9).
- **FR-10.3** 각 카테고리에서 문의 가능한 범위와 Bridge Path가 보유한 대표 레퍼런스를 구분하여 안내한다 (FR-9의 범위/레퍼런스 구분을 진입 화면에서 실제로 드러낸다).
- **FR-10.4** 카테고리 선택 후 해당 제품에 맞는 견적 또는 상담 요청 폼(FR-1)으로 연결한다.
- **FR-10.5** 고객이 자신의 제품 분류를 모르더라도 "기타" 카테고리를 통해 문의할 수 있게 한다.
- **FR-10.6** 카테고리 4(기타)는 "아이웨어·신발·골프용품 외의 제품도 제조 상담, 제품 소싱, 국내외 공장 매칭 및 관련 컨설팅을 문의할 수 있다. 단, 모든 품목의 제작이나 공장 연결을 보장하는 것은 아니며, 접수 후 제품 조건과 대응 가능성을 담당자가 검토한다"는 취지로 안내한다 — 단순 "소싱 컨설팅 전용"이 아니라 포괄적 문의 창구임을 명확히 한다.

버튼 문구, 화면 디자인, 단일 페이지 또는 개별 페이지 구성은 확정하지 않고 UX·디자인 단계로 남긴다.

**해결됨**: FR-1.1의 "예상 수량"이 카테고리 4에 항상 맞지 않는 문제는 FR-1.6(지원 유형별 필수 여부 분기)으로 해결했다.

**판단 근거**: 기존 `estimate.html` 허브와 유사한 구조가 이미 있어 난이도는 낮다. 다만 이게 없으면 방문자가 FR-1에 도달할 방법이 사실상 없어져 MVP 필수로 판단했다.

### 계약·결제 범위 (확정)

정식 견적이 승인된 이후의 계약과 대금 수납은 **웹서비스 범위 밖**에서 처리한다.

- 온라인 카드결제·PG(결제대행) 연동은 MVP 범위에서 제외한다.
- 계약과 입금은 계약서·발주서·정식 견적에 따라 **계좌이체 방식**으로, 웹서비스 외부 절차로 처리한다.
- 계약금·잔금의 비율, 지급 횟수, 지급 시점은 하나의 규칙으로 고정하지 않는다 — 제품, 공장 조건, 샘플·금형 여부, 주문 규모 등에 따라 개별 견적·계약에서 정한다.
- 관리자 화면(FR-5)에서 입금 상태를 관리하는 기능은 현재 MVP 필수에 추가하지 않는다.
- 마이페이지(FR-6)·제작현황(FR-7)을 만들 때 계약·입금 상태 표시가 필요한지는 그때 다시 검토한다 — 이후 버전 후보로 남긴다.

**[OPEN — 운영정책, PRD 범위 밖]** 세금계산서, 계약서, 환불, 결제 증빙 등 구체적인 운영·회계 정책은 별도 운영정책에서 정한다.

| FR-1 견적 입력 폼 | **MVP 필수** | 최소 필수정보(제품종류/수량/간단설명) + 제품별 선택 사양. 여정의 진입점 |
| FR-2 참고 이미지·디자인 파일 첨부 | **MVP 필수** (입력은 고객에게 선택) | 실제 저장·전송까지 포함, 난이도 중간 이상으로 상향 조정됨 |
| FR-3 AI 사전 가격안내 (참고용 예상가격 범위) | **MVP 조건부** | AI는 분류·질문생성만, 가격은 승인된 기준 단가표에서만 산출. 담당자가 준비하는 기준표가 먼저 있어야 동작 |
| FR-4 정식 견적 요청 제출·접수 확인 | **MVP 필수** | 실제 저장·전달·중복방지·실패처리 포함. 서비스가 성립하는 핵심 지점 |
| FR-5 관리자 로그인 및 최소 관리자 화면 | **MVP 필수** (범위는 위 8개 항목으로 제한) | 고객용 로그인/마이페이지와는 별개. 삭제·통계·다중권한·공장계정·내부채팅·자동견적서생성은 제외 |

**흐름 순서로 다시 확인**: FR-8(홈페이지) → FR-9(카테고리 구조) → FR-10(진입 흐름) → FR-1(사양 입력, FR-2 첨부 포함) → FR-3(AI 사전 가격안내, 조건부) → FR-4(제출·접수) → FR-5(담당자 처리). 이 순서로 다시 점검한 결과, 새로 발견된 빈 구간은 FR-10에 적어둔 "카테고리 4의 '예상 수량' 항목이 항상 적용 가능한가" 하나였고, 그 외 특별한 누락은 없었다.

**이후 버전 후보 (지금까지 확인된 것)**: 고객용 로그인·마이페이지(2차), 제작현황(샘플~배송) 추적(3차), 서비스 내부 채팅, 공장·포워더 전용 계정, 자동 견적서 생성, 관리자 통계·다중 권한, 견적 요청 삭제.

**확정**: 고객용 로그인·마이페이지는 **MVP에 포함하지 않는다.** MVP에서 고객은 비회원으로 견적을 요청하고, 접수번호·제출 요약(FR-4.5)과 이메일을 통한 접수 확인·정식 견적서 수신(FR-4.8, FR-5.8)까지만 받는다. 그 이후 소통은 전화·이메일 등 외부 수단으로 처리한다. 로그인·마이페이지(2차 버전)와 제작현황 추적(3차 버전)은 아래 UJ-3·UJ-4·FR-6·FR-7에 장기 여정·기능 요구사항으로 기록해둔다.

## Non-Functional Requirements

지금까지 FR 각 항목에 흩어져 있던 요구사항을 한곳에 모았다.

- **NFR-1 (보안 — 첨부파일 접근 제한)**: 고객의 디자인·로고 등 첨부파일은 허가받지 않은 사람이 접근할 수 없어야 한다. 공개 URL만으로 열람할 수 있는 방식은 금지하며, 파일 형식은 확장자가 아닌 실제 형식·MIME 유형으로 서버에서 검증한다. *(출처: FR-2)*
- **NFR-2 (보안 — 데이터 격리)**: 접수번호만으로 다른 고객의 견적 요청을 조회할 수 없어야 한다. 로그인한 고객(FR-6)은 본인의 견적과 파일만 열람할 수 있어야 한다. *(출처: FR-4, FR-6)*
- **NFR-3 (감사 이력)**: 처리상태 변경 시 변경 전 상태·변경 후 상태·변경한 관리자·변경 일시 네 가지를 기록한다. 정식 견적서 첨부 등 다른 관리자 작업에도 동일한 최소 이력 원칙을 적용한다. *(출처: FR-5)*
- **NFR-4 (신뢰성 — 데이터 보존)**: 이메일 발송, 파일 업로드 등 부가 작업이 실패하더라도, 이미 입력·저장된 견적 요청 본문은 사라지지 않아야 한다. *(출처: FR-2.4, FR-4.4, FR-4.7)*
- **NFR-5 (사용성 — 비전문가 접근성)**: 제조 지식이 부족한 고객도 견적 문의 전 과정을 이해하고 완료할 수 있어야 한다 — 쉬운 설명·예시, "잘 모르겠음"류 선택지를 기본으로 제공한다. *(출처: FR-1)*

구체적인 구현 기술(인증 방식, 저장소, 암호화 등)은 모두 Architecture 단계에서 결정한다 — 이 PRD는 "무엇이 보장되어야 하는가"만 정의한다.

## Future Scope — 2차·3차 버전 (초안, 검토 대기)

MVP 이후를 위해 미리 기록해두는 기능 요구사항. UJ-3·UJ-4를 기반으로 한다.

### FR-6: 고객 로그인 및 마이페이지 (2차 버전 후보)

- **FR-6.1** 고객 로그인 또는 안전한 본인 인증
- **FR-6.2** 본인이 요청한 견적 목록·상세·처리상태 확인
- **FR-6.3** 정식 견적서 확인 및 다운로드
- **FR-6.4** 추가정보와 수정 요청 제출
- **FR-6.5** 계정 생성 시 기존 비회원 견적을 안전하게 연결

**[NFR — 보안]** 접수번호만으로 타 고객 견적 조회 불가(FR-4의 원칙과 동일). 고객은 본인의 견적·파일만 열람 가능.

**[OPEN]** 비회원 견적을 계정에 연결하는 정확한 방식, 로그인·인증 기술은 Architecture 단계에서 결정.

### FR-7: 제작·무역 진행현황 (3차 버전 후보)

- **FR-7.1** 샘플 준비 / 샘플 확인 및 수정 / 생산 준비 / 생산 중 / 검수 / 출고 / 배송 등 진행현황 표시
- **FR-7.2** 단계별 사진과 파일 제공
- **FR-7.3** 주요 상태 변경 시 알림

**[OPEN]** 제작현황 단계 명칭과 고객 공개 범위는 실제 운영 프로세스를 확인한 뒤 확정한다. 내부 관리자 상태(FR-5.5)와 다를 수 있다.
**[OPEN]** 계약·입금 상태(계약금/잔금 지급 여부 등)를 이 화면에 함께 표시할지는 이 기능을 실제로 개발할 때 다시 검토한다 — "계약·결제 범위" 참고.

**MVP·2차·3차 경계**: MVP는 FR-1~5(비회원 견적 요청 + 최소 관리자 화면)까지다. FR-6(고객 로그인·마이페이지)은 2차, FR-7(제작현황 추적)은 3차 버전 후보이며, 둘 다 지금은 구현하지 않는다.
